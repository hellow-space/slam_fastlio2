# TF 发布器生命周期修复与耗时对照（2026-11-13）

已将 TF broadcaster 改为每个 LIVMapper 实例初始化一次，并更新独立计时安装。
原始数学逻辑、坐标系、TF 数值、时间戳生成表达式、发布顺序、队列和线程模型不变。

## 修改

- `include/LIVMapper.h`：新增实例成员 tf_broadcaster_，声明在 node 后，销毁时先释放 broadcaster。
- `src/LIVMapper.cpp`：构造函数体末尾（diagnostics 建立之后）创建并记录一次；publish_odometry 仅调用该成员 sendTransform。
- tf_broadcaster_create 计时事件从逐帧移至初始化；tf_send、odom_publish 和 full_cycle 保留。

## 方法与完整性

使用 /home/nvidia/fastlivo_timing/imu_debug_20261112_210002 的同一份 26.125 秒室内手持数据。
仅以 1x 回放 /livox/imu 和 /livox/lidar，使用 /clock 200 Hz 与 use_sim_time=true。
隔离域固定 176、ROS_LOCALHOST_ONLY=1；轻量订阅 TF、odom 和注册点云，未启动机器人导航。
顺序为 A1、B1、B2、A2、A3、B3；A 为原诊断程序，B 为修复程序。编译期间没有运行性能回放。
排除最初 3 秒，只比较六轮共有的 231 个扫描时间；每版合计 693 帧。P95/P99 为 nearest-rank。
这些计时是 steady_clock 墙钟耗时，包含调度等待；仿真时钟下的消息年龄与实机时钟年龄不应直接等价。

每轮收到全部 5224 条 IMU 与 262 帧 LiDAR，完整周期 262 次，实际 odom/TF 各 258 次。
其余 4 次为初始化阶段。两版都未丢失已发布的 TF/odom；同时间戳 TF 与 odom 的位置一致，
四元数最大分量差约 2.22e-16（tf2 矩阵/四元数转换舍入），使用 1e-12 容差验证。
旧版每轮创建 258 次发布器；新版每轮创建 1 次，三轮都只观察到 1 个 TF 发布端 GID。
旧版图查询观察到 104、104、105 个不同 GID（查询不是逐帧抓取，不能据此计算总创建数）。

共有扫描内，完整周期 >100 ms 的数量为旧版 1/693、新版 0/693。样本太少，不能据此推断稀有事件概率。

## 结论边界

这次可验证的收益是去掉逐帧发布器创建/销毁，发布路径自身耗时显著下降；完整处理耗时仅小幅下降。
该隔离回放中旧版创建耗时也只有毫秒级，没有复现原室内现场约 100 ms 的 TF 创建/替换尖峰。
测试采用本机回环通信、文件日志和轻量订阅，没有原现场完整导航、高程图及网络负载；
不能用这份结果声称现场百毫秒尖峰或室外累计延迟已经消失，需要用更新后的计时版实机复测。
原 bag 从手持运动中途开始，两版均按同样数据重新初始化；本测试验证耗时及发布一致性，不验证绝对定位精度。
